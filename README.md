# CheckStock

Прототип учета товара на складах фулфилмента (ФФ). Менеджер видит, где лежит товар, сколько его доступно, что зарезервировано под FBS и что уже уехало: между ФФ, на склад маркетплейса по FBO, к клиенту по FBS.

Python 3.13, FastAPI, SQLAlchemy 2 (async), Alembic, PostgreSQL 17, Jinja2.

Видео со сквозным сценарием и разбором решений: [docs/demo.mp4](docs/demo.mp4), 4 минуты 40 секунд.

## Запуск

```bash
docker compose up --build
```

Интерфейс откроется на http://localhost:8000. Миграции и тестовые данные накатываются сами: ФФ Север и Юг и приход на них, SKU-101 10 и 6 шт., SKU-102 5 и 0, SKU-103 0 и 4. Повторный запуск данные не дублирует. Начать с чистой базы: `docker compose down -v`.

## Как проверить руками

Сценарий на тестовых данных. Тексты и числа взяты из настоящего прогона.

1. **Остатки.** Все три товара на обоих ФФ, нули тоже видны. Над таблицей строка "Остатки сходятся с историей операций".
2. **FBS.** Заказ WB-1, SKU-101, Север, 3 шт. На Севере: физически 10, доступно 7, резерв 3.
3. **Нехватка.** Заказ WB-2, SKU-101, Север, 9 шт. Ответ: "На ФФ Север доступно 7 из 9, не хватает 2. На других ФФ: Юг: 6". Рядом кнопка "Разделить: Север 7 + Юг 2", она резервирует обе части сразу.
4. **Повторное подтверждение.** Открыть FBS в двух вкладках и нажать "Отправить" у WB-1 в обеих. Вторая вкладка ответит "Заказ WB-1 уже отправлен". На Севере физически 7, к клиенту 3. Если ввести WB-1 заново, ответ будет "Заказ WB-1 по SKU-101 уже отправлен".
5. **Перемещение.** SKU-103 с Юга на Север, 4 шт. До приемки эти 4 шт. числятся в пути между ФФ и не доступны ни на одном ФФ. После кнопки "Принять" они на Севере.
6. **FBO.** SKU-102 с Севера, 2 шт. В таблице "Вне ФФ" у SKU-102 в колонке "FBO в пути" стоит 2. После кнопки "Отметить приемку" эти 2 шт. переходят в колонку "FBO принято".
7. **Удаление ФФ с остатком.** Удалить Юг.
   - Колонка "Юг (удален)" с остатком и резервом остается на экране.
   - Новый резерв, например WB-3, SKU-101, Север, 1 шт., получает ответ: "На ФФ Север доступно 0 из 1, не хватает 1. На других ФФ товара нет. На удаленных ФФ, только перемещением: Юг: 4".
   - Часть WB-2 на Юге можно отправить, а остаток вывезти перемещением на Север.
   - Когда товара на Юге не остается, колонка пропадает.
8. **История.** Каждая операция показывает товар, количество, откуда, куда и документ. Например: `FBS: отправка клиенту | SKU-101 Органайзер | 2 | резерв, Юг (удален) | клиент | Заказ WB-2`.

## Как устроен учет

У каждой пары "товар и ФФ" два числа: физический остаток и резерв FBS. Доступно = физически - резерв, это число не хранится, а считается. Каждое изменение пишется в журнал операций, журнал только дописывается.

| Действие | Физически | Резерв | Доступно | Где товар после |
|---|---|---|---|---|
| Приход | + | | + | на ФФ |
| Резерв FBS | | + | - | на ФФ, в резерве |
| Отправка FBS | - | - | | у клиента |
| Отмена FBS | | - | + | на ФФ |
| Отправка перемещения | - на ФФ-источнике | | - | в пути между ФФ |
| Приемка перемещения | + на ФФ назначения | | + | на ФФ назначения |
| Отгрузка FBO | - | | - | в пути на склад маркетплейса |
| Приемка FBO | | | | на складе маркетплейса |

Остатки сходятся, если выполнены два условия:
- таблица остатков совпадает с пересчетом по журналу;
- для каждого товара пришло = на всех ФФ + в пути между ФФ + FBO в пути + FBO принято + FBS у клиента.

Экран остатков проверяет оба условия при каждом открытии. Тесты проверяют их после каждого шага.

## Ключевые решения

**Остаток защищен базой.** В таблице остатков стоят ограничения: физический остаток и резерв не уходят в минус, резерв не больше физического остатка. Даже ошибка в коде не запишет в учет невозможное.

**Одно действие - одна транзакция.**
- Строки остатка блокируются через `SELECT ... FOR UPDATE`, всегда по возрастанию номера ФФ. Два менеджера не продадут один и тот же остаток и не заблокируют друг друга.
- Подтверждения блокируют строку своего документа и сначала смотрят его статус: отправка и отмена FBS, приемка перемещения и поставки FBO. Повторное нажатие отвечает, что документ уже проведен, и ничего не списывает.

**Повторная отправка формы.**
- У каждой формы скрытый ключ. Учет сохраняет его вместе с содержимым операции в той же транзакции, поэтому двойной клик и одновременные запросы проводят операцию один раз.
- Страницы не кэшируются, а формы не восстанавливают введенные значения. После кнопки "Назад" форма пустая, и повторить операцию можно только осознанно.
- Один заказ FBS по одному товару нельзя зарезервировать второй раз, пока его не отменили.

**Нехватка проверяется на выбранном ФФ, а не по сумме.** Сумма по всем ФФ нужна только для подсказки. Система ничего не берет с других ФФ молча: она пишет, сколько есть на выбранном ФФ и где еще, и предлагает разделить резерв или отгрузку FBO. Все части создаются в одной транзакции: либо все, либо ни одной. Перемещение отправляется только с выбранного ФФ, при нехватке система отказывает и подсказывает.

**Удаление ФФ - это архив.** Остатки и история удаленного ФФ должны сохраниться, поэтому ФФ получает пометку "удален", а остатки и журнал не меняются.
- Пока на удаленном ФФ есть товар, он виден на экране остатков.
- На удаленный ФФ нельзя оформить приход, перемещение или резерв, с него нельзя отгрузить FBO. Товар с него можно только вывезти перемещением.
- Начатое доводится до конца: заказ отправляется, перемещение принимается.
- Название удаленного ФФ можно отдать новому, история их различает.

**Экран читается одним снимком базы.** Остатки, товар в пути и сверка читаются в одной транзакции REPEATABLE READ. Иначе перемещение, проведенное между двумя запросами, на мгновение показало бы товар дважды или ни разу.

**Интерфейс без сборки фронтенда.** Страницы на Jinja2, действия - обычные формы с переадресацией после отправки. У страницы две раскладки, для компьютера и для телефона, их переключает ширина экрана. Поля и тексты у раскладок общие.

Магазин один, отдельной сущности для него нет. Товары берутся из тестовых данных, создавать их в интерфейсе не требуется. Перемещение и поставка FBO принимаются целиком.

## Тесты

```bash
docker compose run --rm app pytest
```

Тесты идут на настоящем PostgreSQL, в отдельной базе `checkstock_test`, которая создается заново при каждом запуске. Блокировки, ограничения базы и гонки на подставных объектах не проверить.

- **Учет.** Каждый складской сценарий на тестовых данных. После каждого шага экран остатков сверяется с журналом.
- **Гонки.** Параллельные резервы одного остатка, одновременные подтверждения одной отправки, одна форма несколько раз одновременно, удаление ФФ во время операции.
- **Случайные цепочки.** Hypothesis генерирует цепочки до 30 действий и сверяет каждый шаг с отдельно написанной моделью учета. Отказ не должен оставлять следов.
- **Страницы.** Тест открывает страницу и отправляет форму так, как это сделал бы браузер, в версиях для компьютера и для телефона.

Линтеры и типы:

```bash
docker compose run --rm app sh -c "ruff check . && ruff format --check . && mypy app tests migrations/env.py"
```

## Структура

- `app/inventory.py` - весь учет: операции, блокировки, проверки, сверка;
- `app/web.py` и `app/templates/` - страницы и формы;
- `app/models.py` и `migrations/` - схема;
- `app/seed.py` - тестовые данные.

## Настройки

`DATABASE_URL` - адрес PostgreSQL, в `docker-compose.yml` он уже задан.
